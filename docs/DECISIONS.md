| 1 | 2026-11-25 | Amit Raz with Claude | **Bidi control characters (U+200E, U+200F, U+061C, U+202A–U+202E, U+2066–U+2069) are stripped from every transcript at render time, in `transcript_output.clean_text()`; a segment that is only such characters is dropped.** Why: the Hebrew model (`ivrit-ai/whisper-large-v3-ct2`) emitted U+202B on 159 of 458 lines of a real 28-minute call, sometimes mid-line; they are invisible but break searching and later processing of the text, and a plain-text editor lays out Hebrew right to left without them. Rendering is the one point that covers both engines (mlx-whisper and faster-whisper) and both transcript kinds. Rejected: stripping inside each engine — two places to keep in sync, and the mlx path could not be run on this machine; stripping in `diarization.merge` — it would only cover labelled transcripts, and diarization cannot import `transcript_output` (which imports diarization) without a cycle; leaving them in — the original behaviour, with the search breakage above. Revisit if a consumer needs the model's raw text (it would need a separate raw output, not this file). Proof: 9 tests in `tests/test_transcript_output.py`; the real file re-run gave 0 controls in 458 lines. Files: `transcript_output.py`, `tests/test_transcript_output.py`, `README.md`. |
| 2 | 2026-11-25 | Amit Raz with Claude | **The two tests that failed on Windows were fixed to run on every platform, not skipped on Windows.** Why: both were test bugs and the code under test was correct on Windows. The cp1252 stream test now passes `newline="\n"` so the platform line ending does not enter the bytes it compares; the macOS drag-and-drop test builds its path with forward slashes so its own folder separators are not unescaped. Rejected: `skipIf(win32)` — it would hide the behaviour on the platform where the UTF-8 stream fix matters most. Proof: full suite 178 tests OK on Windows. Files: `tests/test_platform_support.py`. |
| 3 | 2026-11-25 | Amit Raz with Claude | **When torch is installed, the CUDA library probe looks in `torch/lib` before the `nvidia.*` pip packages, so CTranslate2 and torch share torch's bundled cuDNN.** Why: on Windows the CUDA torch wheel (2.14.1+cu126) bundles cuDNN 9.10.2 under the same DLL names as `nvidia-cudnn-cu12` (9.28.1.4, installed by `install.py --gpu`). Whichever loads first owns the name in the process. The probe loaded 9.28 first, so `import torch` for diarization failed with `WinError 127` on `cudnn_cnn64_9.dll`; torch-first loads succeed and CTranslate2 4.9.1 runs on 9.10 at the same speed (96.8 s vs 97.7 s before, same 458 lines). On Linux the torch wheel takes cuDNN from the same `nvidia-*` pip packages, so the order makes no difference there. Rejected: importing torch before the probe — loads torch (~2 s, several GB of DLLs) on every plain run; dropping `nvidia-cudnn-cu12` when installing with diarization — existing installs keep it, and the probe would still load it first if torch were ever removed; pinning `nvidia-cudnn-cu12` to torch's cuDNN — breaks on every torch upgrade. Revisit if a torch build stops bundling cuDNN on Windows, or if CTranslate2 needs a newer cuDNN than torch ships. Proof: real `--speakers auto` run exit 0 on `cuda` for both stages; `tests/test_cuda_libraries.py` asserts the order; suite 178 OK. Files: `engines/cuda_libraries.py`, `tests/test_cuda_libraries.py`, `README.md`. |
| 4 | 2026-11-27 | Amit Raz with Claude | **The transcriber ships as a Claude Code plugin from this repo (`audio-transcriber`, its own marketplace), invoked as `/transcribe <audio>`; the skill calls one stdlib script, `plugin_runner.py`, which keeps transcript text out of Claude's context.** Chosen by Amit on 2026-11-27. Why each part: (a) A plugin in this repo installs on any machine with two `/plugin` commands and updates with the code. Rejected: a personal skill in `~/.claude/skills` (one machine only, copied by hand); an MCP server (no plain slash command, and a long-running server process for a job that runs a few times a day). (b) A plugin installed from GitHub lives in a cache folder that Claude Code replaces on every update, so its venv goes in `${CLAUDE_PLUGIN_DATA}/venv` through the new `install.py --venv-dir`; a clone loaded in place reuses its own `.venv` first. A hash of both requirements files is saved after a data-folder install, so an update that changes them is noticed and a re-install offered. (c) No session-start hook to install: it would need a separate Windows variant and could start a multi-GB install nobody asked for. The install happens on first use, after an explicit yes. (d) The child's stderr goes to `<data>/logs/last-run.log` and is never printed, because Whisper prints every transcribed segment there; the runner prints only the JSON result, the validation message for exit codes 2, 3 and 4 (raised before any model runs), and for exit code 1 only the part after cli.py's `Failed:` marker, else just the log path. The skill also tells Claude not to open the transcript or logs unless asked, since reading them sends the text to Anthropic. (e) `plugin.json` has no `version`, so every pushed commit counts as an update (`claude plugin validate` warns about this; the warning is accepted). Revisit if Claude Code starts keeping the install folder across updates, gains a per-plugin install hook that runs on both platforms and can ask first, or if Amit wants transcript text in context by default. Proof: `tests/test_plugin_runner.py` (31 tests, including segment text in a fake stderr never reaching stdout for exit 0, 1 and a killed child) and 7 new `--venv-dir` tests; suite 216 OK; real runs from the repo venv and from a copy without `.venv` installed into a scratch data folder (see PROGRESS 2026-11-27). Files: `plugin_runner.py`, `claude_plugin/`, `install.py`, `.claude-plugin/`, `skills/transcribe/SKILL.md`, `tests/test_plugin_runner.py`, `tests/test_installer.py`, `README.md`. |
| 5 | 2026-11-27 | Amit Raz with Claude | **In the plugin, speaker naming happens in a terminal window that the plugin opens on the user's own screen after a labelled transcription; Claude learns only whether the window opened.** Chosen by Amit on 2026-11-27 after a real run where the naming step he knows from the terminal script did not happen. Why: naming needs each speaker's sample lines on screen, and anything Claude shows the user has first been sent to Anthropic, because the model does not run on the user's machine. A window started by the runner prints straight from the script to the screen, so the step is part of the flow and the "transcript text stays local" rule of row 4 still holds. Rejected: (A) Claude shows up to three excerpts per speaker in a question dialog (simplest to build, but sends transcript lines to Anthropic on every run and breaks the README's promise); (B) Claude asks using only talk-time share and first-line times (local, but the user never sees what was said, which is what makes a speaker recognisable); (C) keep handing the user a command to paste (local, but it is not part of the flow, which is the complaint). Reverse this only if the privacy rule itself is dropped or a host offers a way to show local text without sending it. Proof: 2026-11-27 progress entry; `tests/test_naming_window.py` asserts the JSON is ASCII and holds no transcript text. |
| 6 | 2026-11-27 | Amit Raz with Claude | **How the naming window opens: on macOS a self-deleting `.command` script opened with `/usr/bin/open -a Terminal`, on Windows the naming program started with `CREATE_NEW_CONSOLE`, on Linux the first terminal emulator found; a window that cannot open is reported as `opened` false with a reason and a paste-ready command, exit 0; the runner accepts a transcript by its `N speaker(s) detected:` first line, not by its file name.** Why each part: (a) `osascript` telling Terminal to `do script` sends Apple events, which macOS gates behind a one-time Automation consent for whichever app hosts Claude Code, and a "Don't Allow" click blocks it until the user changes Privacy & Security settings (Apple: "Allow apps to control your Mac", `NSAppleEventsUsageDescription`); opening a file needs no consent. The paths sit inside the script quoted with `shlex.quote`, so neither Terminal nor AppleScript parses a path with spaces, quotes or Hebrew. `-a Terminal` keeps it working when `.command` files are set to open in an editor. (b) Exit 0 on a fallback lets the skill read one field, `opened`, and never treat "no window" as a failed transcription. (c) `--out` and the `_2` name bumping produce transcripts that do not end in `_speakers.txt`, and the header line is not transcript speech. Rejected: `osascript` (the consent dialog, and not tried for real to avoid raising it); a non-zero exit on fallback (the skill would need a second error table); a file-name check (refuses valid transcripts). Not settled: Windows and Linux have never been run, see `docs/tickets/naming-window-never-run-on-windows-or-linux.md`; the window is always Terminal.app, see `docs/tickets/naming-window-on-macos-always-uses-terminal-app.md`. Proof: macOS run in the 2026-11-27 progress entry (0.17 s, `"method": "macos_terminal_command_file"`); 250 tests OK. |
